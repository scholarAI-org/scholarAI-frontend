## 2. منهجية العمل التي نتبعها

المنهجية الموثقة هي: **مواصفات → خطة تقنية → مهام صغيرة → تنفيذ تدريجي → اختبارات → تحقق بصري وتوثيق النتائج**.

1. نراجع الكود الموجود والعقد مع الباك اند قبل إنشاء مكوّنات جديدة.
2. نكتب نطاق الميزة وسلوكها وحالات القبول في `spec.md`.
3. نحول المتطلبات إلى قرارات معمارية وهيكل ملفات في `plan.md`.
4. نقسم التنفيذ إلى مهام مرقمة في `tasks.md`، مع شروط جاهزية في checklist.
5. نبدأ بالعقد والأنواع وحالة الرابط والبيانات، ثم الترجمة والـ Student Shell، ثم واجهة البحث والتفاعلات.
6. ننفذ كل مجموعة مترابطة ونتحقق منها قبل اعتبارها مكتملة. وجود دالة API لا يعني اكتمال التفاعل الذي يستخدمها.
7. نستخدم Figma لفهم التصميم، ونبني مكونات دلالية باستخدام نظام المشروع. لا ننسخ React المولّد من Figma حرفيًا.
8. نقارن الواجهة مع التصميم، ونراجع العربية/RTL والإنجليزية/LTR وأحجام الشاشات ولوحة المفاتيح.
9. نحدّث المهام وتوثيق التحقق بالنتائج الفعلية، ثم نكتب كوميت يصف التغيير المحدد.

مرجع القواعد العامة الموجود حاليًا: `.specify/memory/constitution.md`. المشروع يستخدم Next.js App Router وTypeScript وTailwind وnext-intl وReact Query، مع `AuthProvider` و`RoleGuard`. نلتزم بهذه البنية ونستفيد من الموجود بدل إنشاء أنظمة موازية.

أسلوب الكوميتات المستخدم هو Conventional Commits، مثل `feat(student-scholarships): ...`. لا يوجد في هذا التسليم دليل على تنفيذ أدوات Spec Kit فعليًا؛ الموجود هو وثائق بأسلوبها وإشارة إلى `/speckit.implement` داخل checklist.

## 4. ما أُنجز فعليًا في الكوميت af02fc9

الملفات البرمجية السبعة تقع تحت `src/features/student/scholarship-discovery/`:

| الملف                          | الموجود فعليًا                                                                           | حدود الإنجاز                                                                  |
| ------------------------------ | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `types.ts`                     | أنواع الفلاتر والترتيب والاستجابة، `DiscoveryQuery`، نموذج البطاقة وواجهة match مستقبلية | نوع التفاصيل حاليًا يساوي نوع بطاقة الاكتشاف؛ يحتاج مراجعة مقابل عقد التفاصيل |
| `constants.ts`                 | الفلاتر المدعومة، الترتيب الافتراضي، query افتراضي وحجم صفحة 20                          | لا توجد واجهة تستخدمها بعد                                                    |
| `lib/discovery-query-state.ts` | `parseDiscoveryQuery` و`serializeDiscoveryQuery`                                         | أدوات تحويل فقط؛ ليست hook تزامن مع الراوتر                                   |
| `query-keys.ts`                | مفاتيح discovery/details/saved/filterOptions وعائلاتها                                   | وجود saved keys لا يعني وجود صفحة محفوظات أو جلب بياناتها                     |
| `api/scholarships.ts`          | طلبات البحث وخيارات الدول والتفاصيل والحفظ وإلغاء الحفظ عبر `apiClient`                  | لا توجد mutations أو إدارة optimistic cache بعد                               |
| `hooks/useScholarships.ts`     | `useScholarshipDiscovery` و`useScholarshipFilterOptions` و`useScholarshipDetail`         | hooks مجمعة في ملف واحد حاليًا، بخلاف أسماء الملفات المقترحة في الخطة         |
| `adapters/scholarship.ts`      | تحويل بطاقة API إلى نموذج عرض واختيار عنوان محلي وتنظيف الحقول الاختيارية                | لا يتحقق من صحة URL الصورة أو التاريخ أو بنية response وقت التشغيل            |

### سلوك الأساس المكتوب

- البحث: إزالة الفراغات الطرفية ودمج الفراغات المتكررة، وإهمال البحث الفارغ.
- الفلاتر: معاملات متكررة، مع تنظيف قيم enums وإزالة المكرر والقيم غير المدعومة.
- الدول: تنظيف الفراغات وإزالة القيم الفارغة والمكررة، دون تحويلها إلى أكواد ISO.
- الترتيب: `newest` أو `deadline_soon`؛ قراءة `deadline_soonest` وتحويله إلى `deadline_soon`.
- الصفحة: رقم صحيح موجب، وإلا تصبح 1.
- تسلسل الرابط: إهمال sort الافتراضي وpage=1؛ `page_size=20` يضاف إلى طلب API فقط.
- discovery query يستخدم `placeholderData: keepPreviousData`.
- خيارات الدول لها query مستقل و`staleTime` مدته 30 دقيقة.
- سياسة retry تمنع إعادة المحاولة لأخطاء `401` و`403` و`422`، وتسمح بعدد محدود للباقي.
- تفاصيل المنحة لا تُطلب إلا إذا كان ID عددًا صحيحًا موجبًا.
- adapter يفضل `title_ar` للعربية أو `title_en` للإنجليزية ثم `title`، ويضع `match: null`.
- طلبات GET تمرر `AbortSignal`. دالتا save/unsave الحاليتان لا تقبلانه.

هذه نتائج قراءة للكود، وليست تقرير نجاح اختبارات أو اتصال فعلي بالباك اند.

## 5. النواقص التي يجب استكمالها قبل بناء الواجهة

1. مراجعة استجابات OpenAPI الفعلية، خاصة التفاصيل وnullable fields؛ TypeScript وحده لا يتحقق من JSON وقت التشغيل.
2. إضافة parsing دفاعي لاستجابة خيارات الدول؛ الدالة الحالية تُرجع response typed فقط، بينما T017 يطلب التحقق من `countries: string[]`.
3. توحيد اسم دالة خيارات الدول: الموجود `getScholarshipFilterOptions`، بينما T017 يذكر `getScholarshipDiscoveryFilterOptions`. حدّث الكود أو الوثائق بشكل متسق.
4. إضافة `useDiscoveryQueryState` وربطه بالراوتر locale-aware. reset الصفحة وBack/Forward والـ debounce غير منفذة بمجرد وجود parser/serializer.
5. التأكد من أن query الذي يصل إلى hook وAPI مطبّع. discovery hook الحالي لا يحتوي positive-page guard مستقلًا؛ لا تعتمد على تمرير query سليم دائمًا دون تحديد مسؤولية ذلك.
6. إضافة اختبارات الأساس. ملف `tests/student-scholarship-discovery.test.mjs` غير مضاف ضمن كوميت الأساس.
7. مراجعة اختلاف أسماء حقول match بين نص المواصفات والكود؛ اعتمد نموذجًا واحدًا دون إضافة بيانات مطابقة فعلية.

## 6. ما لم يُنجز بعد

لا توجد صفحة بحث للطالب أو مكونات واجهتها في البرانشات التي فُحصت. وجود «البحث عن منح» في قائمة Profile الحالية مجرد عنصر واجهة؛ لا يثبت وجود route وظيفي.

- لا يوجد `StudentShell` مشترك؛ layout الطالب الحالي يحتوي `RoleGuard` فقط، وProfile يركّب إطاره محليًا.
- لا يوجد مسار `/[locale]/student/scholarships` أو مسار تفاصيل `/[locale]/student/scholarships/[id]`.
- لا توجد toolbar أو فلاتر أو Grid/List أو بطاقات نتائج.
- لا توجد translations خاصة بهذه الواجهة أو حوارات navigation/filters الجديدة.
- لا توجد bookmark mutation hook، أو optimistic updates، أو rollback، أو منع طلبات الحفظ المتكررة.
- لا توجد helpers للمواعيد أو نافذة pagination أو حالات loading/empty/error الخاصة بالصفحة.
- لا يوجد إثبات لفحص Figma أو مطابقة التصميم أو تحقق RTL/LTR أو mobile لهذه الميزة.
- لا يوجد تقرير تحقق نهائي للميزة. لم نُشغّل build أو lint أو اختبارات الميزة أثناء إعداد هذا المستند.

## 7. القرارات المعمارية المطلوب الحفاظ عليها

### المسارات والـ Student Shell

المسارات المعتمدة في الخطة:

```text
/[locale]/student/profile
/[locale]/student/scholarships
/[locale]/student/scholarships/[id]
```

`src/features/student/layout/` يملك StudentShell والهيدر والسايدبار والتنقل للموبايل. يلف `student/layout.tsx` المحتوى بالـ shell مع الإبقاء على `RoleGuard`. صفحات البحث والتفاصيل تكون thin Server Components تفوض العرض والتفاعل إلى feature components.

Profile الحالي Client Component ويمتلك Navbar وSidebar وProfileLayout. نفّذ نقل الإطار تدريجيًا حتى لا تظهر نسختان من الهيدر/السايدبار، مع الحفاظ على النماذج وhooks والهوية ورفع الصورة. لا تعتبر هذا النقل منجزًا.

التنقل الجديد يفعّل Profile والبحث فقط؛ لا يضيف صفحات وهمية أو عدادات إشعارات وهمية أو theme control. المصادقة والهوية تأتيان من النظام الموجود، دون auth store جديد.

### مصدر حالة البحث

الرابط هو المصدر الأساسي لـ search/filter/sort/page. الحقول متعددة الاختيار تُرسل بمعاملات متكررة، مثل:

```text
?academic_level=bachelor&academic_level=master&country=Germany&sort=deadline_soon&page=2
```

حسب الوثائق المحفوظة، الاختيارات داخل المجموعة OR وبين المجموعات AND؛ راجع ذلك مع العقد. البحث والفلترة والترتيب والتقسيم إلى صفحات تتم في الباك اند، ولا نفلتر صفحة النتائج محليًا.

تغيير البحث/الفلاتر/الترتيب يعيد page إلى 1. pagination يغيّر page فقط. input البحث يحتفظ بمسودة مؤقتة وdebounce قرابة 300ms، ويعيد مزامنتها عند Back/Forward. Grid/List حالة عرض في الذاكرة، خارج الرابط ومفاتيح queries؛ تغييره لا يعيد جلب النتائج أو الدول.

### عقد API

| العملية      | endpoint                               |
| ------------ | -------------------------------------- |
| البحث        | `GET /api/scholarships/`               |
| خيارات الدول | `GET /api/scholarships/filter-options` |
| التفاصيل     | `GET /api/scholarships/{id}`           |
| الحفظ        | `POST /api/scholarships/{id}/save`     |
| إلغاء الحفظ  | `DELETE /api/scholarships/{id}/save`   |

الفلاتر: academic level = `bachelor/master/phd/exchange`، funding = `full/partial`، opportunity = `scholarship/academic_exchange/research_fellowship/training`. الترتيب المعروض فقط newest وdeadline soon.

مصدر الدول الوحيد هو filter-options؛ اعرض وأرسل السلسلة المرجعة نفسها، دون قائمة دول ثابتة أو مكتبة أكواد ISO. فشل خيارات الدول له حالة مستقلة ولا يمنع ظهور نتائج المنح.

### البطاقات والحفظ

Grid وList يستهلكان نفس `ScholarshipCardModel` ونفس الأفعال. العدد من `response.total`، والصفحات من بيانات السيرفر. لا نضيف بيانات جامعة أو تمويل أو موعد أو matching غير موجودة.

حفظ المنحة يحتاج منع طلب مكرر لكل ID، وsnapshot للكاش المتأثر، وoptimistic update ثم rollback دقيق عند الفشل. عند الاستقرار نعمل invalidation لعائلات `discoveries()` و`detail(id)` و`savedLists()` ذات الصلة، وليس `all` أو queries غير مرتبطة. لا نخزن الحفظ في localStorage.

الـ match اختياري للمستقبل فقط؛ badge لا يظهر عند غيابه، ولا نحسب score في المتصفح ولا نعرض highest-match sort.

### التصميم واللغات والوصول

قبل UI أضف namespaces عربية وإنجليزية: `StudentLayout` و`StudentScholarshipDiscovery` و`StudentScholarshipDetails`، بما فيها نصوص ARIA والأخطاء والأعداد بصيغ الجمع.

Figma nodes المرجعية: `2262:3331` للبحث و`2264:3472` للحالة الفارغة. رابط ملف Figma الكامل غير موثق في المصادر التي تمت مراجعتها؛ لا تخمّن file key. افحص التصميم قبل التنفيذ البصري، واستخدم tokens ومكونات المشروع وflex/grid، لا نسخًا حرفيًا للكود المولّد. إذا كانت بيئة التنفيذ توفر مهارات Figma، اتبع prerequisite المناسب قبل استدعاء أدواتها.

صور المنح تأتي من hosts يحددها الباك اند: تستخدم الخطة `<img>` مع lazy loading وalt مناسب ومساحة ثابتة والتحقق من URL وfallback محلي محايد عند الفشل. لا تستخدم صور Figma كبيانات بديلة، ولا روابط MCP المؤقتة، ولا توسع allowlist عالميًا. أي suppression لقاعدة `@next/next/no-img-element` يكون موثقًا ومحدودًا في مكوّن الصورة.

الديسكتوب: عمودان للـ Grid بجانب الفلاتر. الموبايل: عمود واحد وفلاتر داخل dialog قابل للاستخدام بلوحة المفاتيح. حوارات الموبايل تحتاج تسمية وEscape وإدارة focus وإعادته إلى trigger. اختبر RTL/LTR والتركيز وترتيب القراءة وعدم overflow.

التفاصيل في هذه الميزة ملخص واقعي فقط، مع ID صحيح وloading/401/403/404/error وعودة للبحث وحفظ متسق. التصميم الكامل للتفاصيل مؤجل.

6. تنفيذ الحفظ والكاش والrollback: T036–T040.
7. المواعيد والpagination وحالات البيانات: T041–T047.
8. dialogs والموبايل وRTL/LTR: T048–T051.
